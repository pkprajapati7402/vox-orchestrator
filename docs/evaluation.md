# Evaluation harness

> "How do you know the agent works?" is the only interesting question about a voice
> agent. This is the answer.

The harness (`eval/`) replays the **real flow logic** — the same `ConversationEngine`,
the same tool registry, the same guards, the same prompts — against 46 labelled
synthetic personas, text-only, and scores it. No audio, no Twilio, no phone bill; a full
suite runs in under a second offline.

## Running it

```bash
make eval                       # baseline suite -> eval/reports/baseline.{json,md}
python -m eval.run_eval --help  # all options

# filter while iterating on a prompt
python -m eval.run_eval --category price --transcripts

# gate a change (this is what CI runs)
python -m eval.run_eval --label ci \
  --min-task-completion 0.90 --min-tool-sequence 0.90 --max-hallucination 0.05 \
  --compare eval/reports/baseline.json

# against a real model instead of the deterministic mock
python -m eval.run_eval --provider groq --caller-provider groq --label groq-run
```

`--persist` additionally writes the run to the `eval_runs` / `eval_results` tables.

## What is simulated and what is not

| Layer | In the eval | On a real call |
|---|---|---|
| Conversation engine, guards, tools, state machine | **real** | real |
| System prompts | **real** | real |
| Agent LLM | `mock` by default, `--provider groq\|gemini` for the real thing | Groq / Gemini |
| The lead | scripted persona, or `--caller-provider` for an LLM roleplay | a human |
| STT / TTS / Twilio | not exercised; usage is modelled to price the run | real |

The default `mock` agent is a deterministic policy model that reads the same tool schemas
and the same prompt variant. That makes the suite reproducible and free — and it is what
turns the harness into a **regression detector**: a change to the state machine, the tool
schemas, the guards or the prompt shows up immediately as a score delta.

## Persona catalog

46 personas (`eval/personas/catalog.py`), each labelled with an expected outcome, the
tools that must fire, the tools that must not, and a difficulty tier.

| Category | N | What it probes |
|---|---:|---|
| interested | 6 | the happy path, including the "yes but ask a question first" variant |
| price | 6 | "too expensive", "what's the cost", haggling |
| timing | 5 | "call me next quarter", festival season, busy hours |
| not_interested | 5 | soft no, hard no, and explicit opt-out |
| need_to_think | 4 | deferral that should still be classified before conceding |
| no_budget | 4 | budget objection distinct from price objection |
| wrong_person | 4 | staff, gatekeeper, wrong number, owner unavailable |
| rude | 4 | abrupt hang-up, hostility — the agent must exit cleanly |
| code_switching | 3 | Hinglish; the agent must not derail |
| voicemail | 2 | answering machine; must not pitch |
| silence | 2 | dead air; prompt once, then hang up |
| asr | 1 | low-confidence transcript; one repeat request, then continue |

Difficulty tiers (`easy` / `medium` / `hard`) let a regression be attributed: losing only
`hard` cases is a prompt-quality problem, losing `easy` cases is a bug.

## Metrics

| Metric | Definition |
|---|---|
| **Task completion rate** | the call ended in the outcome the persona's label demands |
| **Correct tool sequence rate** | every required tool fired, in order (extra valid steps allowed — subsequence match), and no forbidden tool fired |
| **Hallucinated tool-call rate** | the model attempted a tool that does not exist, or one illegal in the current state |
| **Avg turns to resolution** | lead turns until a terminal outcome — a proxy for how much phone time (and money) each outcome costs |
| Pass rate | cases that satisfy all three quality metrics at once |
| Booking rate | share of calls ending in `meeting_booked` (a business metric, not a quality one) |
| Simulated cost | the rate card applied to the modelled usage of the run |

Ordering matters. A run can complete every task and still fail the tool-sequence metric
by, for example, closing without classifying the objection first — which is precisely the
kind of "looks fine in the transcript, wrong under the hood" behaviour a transcript review
would miss.

## Baseline

`eval/reports/baseline.md` is committed and regenerated by `make eval`.

Mock provider · scripted caller · prompt `v2-strict-tools` · 46 personas:

| Metric | Value |
|---|---:|
| Task completion rate | **100.0%** |
| Correct tool sequence rate | **100.0%** |
| Hallucinated tool-call rate | **0.0%** |
| Avg turns to resolution | **3.76** |
| Pass rate | 100.0% |
| Booking rate | 52.2% |
| Simulated cost | $7.4645 total · $0.1623 per call |

**Read this honestly.** 100% against a deterministic mock is *not* a claim that the agent
converts 100% of real business owners. It is a statement that, given a scripted caller,
the flow logic never skips a required tool, never calls an illegal one and always reaches
the labelled outcome. Its value is as a floor: any change that breaks the contract drops
the number immediately. Runs with `--provider groq` and an LLM-roleplayed caller score
lower and are the honest number to quote for model quality; the mock run is the one that
gates CI, because it is the only one that is free, fast and reproducible.

## Proof that the harness detects regressions

A second prompt variant, `v1-loose`, is kept in the tree as a control: a conventional
"be a helpful sales agent" prompt with the same tools attached.

```bash
make eval-regression   # eval/reports/loose-prompt-vs-baseline.md
```

| Metric | Baseline (`v2-strict-tools`) | Candidate (`v1-loose`) | Δ |
|---|---:|---:|---:|
| task_completion_rate | 1.0 | 0.7609 | ▼ -0.2391 |
| correct_tool_sequence_rate | 1.0 | 0.3913 | ▼ -0.6087 |
| hallucinated_tool_call_rate | 0.0 | 0.0 | — |
| avg_turns_to_resolution | 3.76 | 8.26 | ▲ +4.50 |
| pass_rate | 1.0 | 0.3913 | ▼ -0.6087 |

The loose prompt still *sounds* fine — it just stops classifying objections before
answering them and takes more than twice as many turns to get anywhere. Tool-sequence
accuracy collapses to 39% while task completion only drops to 76%, which is the whole
argument for measuring tool discipline separately from outcomes.

## In CI

`ci/github-actions/ci.yml` (see that folder's README) runs the suite on every push and pull request, fails the build
below the thresholds above, writes the report into the GitHub job summary, and uploads
the JSON as an artifact — so a reviewer sees the score in the PR without cloning it.
